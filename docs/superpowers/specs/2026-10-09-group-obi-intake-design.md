# LINEグループから帯替えを依頼し、グループに完成リンクを返す 設計

日付：2026-10-09（Codex レビュー1回目の指摘を反映：同日）　決定者：下村さん（会話で承認）
関係するリポジトリ：
- `apps/aisecretary`（公式アカウント「MD NEXT秘書」の Webhook。Vercel）…この設計書の置き場所
- `apps/reins-report`（portal。Railway）
- `apps/line-secretary`（Mac の LINE秘書。launchd）と、その中の `delivery/`（閲覧ページ。Vercel `mdnext-doc-delivery`）

## 目的
今は帯替えの依頼を LINE WORKS の秘書室からしか出せず、完成リンクも秘書室にしか届かない。社長などがグループ（【MDNEXT】業務指示＝`tools/line-send/宛先.json` の「営業部」。aisecretary の `LINE_GROUP_ID` と同じ）に貼った PDF を、下村さんがグループの中で一言頼むだけで帯替えし、グループに完成リンクが届くようにする。

## 決めたこと（会話で下村さんが決めたもの）
1. **依頼できるのは下村さんだけ**
2. **使う PDF は、依頼の時点からさかのぼって30分以内にそのグループに出た PDF**（誰が貼ったものでもよい）
3. **運ぶのは MD NEXT秘書**（依頼を受けたその場で portal に送る。Mac が止まっていても受付と下準備は進む）
4. **受付の返事と完成リンクはグループに**。秘書室にも控え
5. **グループに出したリンクは、グループの一員なら開ける**（名簿の登録は要らない）

## 決めたこと（設計で決めたもの。Codex の指摘への答え）
6. **受付の入口で「どこから・誰から」を固定し、合わなければ何もしない（fail closed）**
   - `source.type === 'group'` かつ `source.groupId === LINE_GROUP_ID`（営業部）だけ。個別トーク・他のグループでは帯替えとして扱わず、portal を呼ばず、PDF の控えも作らない
   - 発言者の `source.userId` が `JOB_ALLOWED_USER_IDS`（カンマ区切りの LINE userId。`U` で始まる33文字）のどれかと完全一致すること
   - `LINE_GROUP_ID`・`JOB_ALLOWED_USER_IDS`・`PORTAL_BASE_URL`・`JOB_API_TOKEN` のどれかが未設定・形が不正なら、帯替えの受付は全部止める（依頼の形の発言には「いま帯替えの受付を止めています」）
   - 営業部のグループで、許可リストにない人が依頼の形で送ったら「帯替えの依頼は下村さんからお願いします」とだけ返す
7. **依頼の形**：本文の先頭（メンションを除いた後）が依頼語で始まるもの。依頼語と物件名・`担当:` の読み方は line-secretary の `src/jobs/parse.js` と同じ（`帯替え・帯かえ・帯変え・オビ替え・おび替え`、区切り、filler）。**同じ入力から同じ結果になることを、共通のテスト用データ（JSON）を両リポジトリに置いて固定する**
8. **メールの下書きとの優先**：帯替えの判定は、メンションがあり、かつ本文の先頭が依頼語のときだけ。このときは進行中のメール下書きより先に帯替えとして扱う（メール本文の途中に「帯替え」があっても、先頭でなければ帯替えにならない）。それ以外は今までどおりの順番
9. **PDF の控え**（帯替え専用。既存のメール・タスク用の控えは変えない）
   - 営業部のグループに出た `file` メッセージのうち、ファイル名が `.pdf`（大文字小文字を問わない）のものだけ
   - 控える中身：message.id・ファイル名・大きさ・**LINE のイベントの時刻（timestamp）**・貼った人の userId
   - 置き場：Vercel KV の sorted set（score＝イベントの時刻）。`zadd` で足す（同時に届いても上書きしない）。古いものは追加のときに `zremrangebyscore` で消し、キー全体の期限は1時間
   - 依頼のときに、依頼のイベントの時刻から30分以内のものを、時刻の古い順に最大20件取る。依頼より後に出たものは使わない
10. **受付は1回の処理で最後まで行う（同期）**
    - Webhook の関数の実行時間を `maxDuration = 60`（秒）にする（Vercel のプランで許される値か、計画の最初に確かめる。許されなければ止めて相談）
    - 受け付ける大きさ：**合計25MBまで**（1件の上限は portal と同じ40MiB だが、合計で先に断る）。超えたら断る
    - 時間の配分：LINE からの取得は1件15秒・全体30秒まで、portal への送信は全体20秒まで。超えたら失敗として扱う
    - 既存のイベント予約（3分）より短いので、別の処理が同じ依頼を引き継ぐことはない
11. **PDF は全部取れたときだけ受付ける**：1件でも取れない（LINE 側の保存期間切れなど）、`%PDF-` で始まらない、なら受付全体をやめて理由を返す（受付の返事に書いたファイルと portal に入ったファイルを必ず一致させる）
12. **portal の受付を1回の呼び出しにまとめる（途中で切れても残らない）**
    - portal に新しい入口 `POST /api/jobs/intake`（multipart：依頼の項目＋PDF）を作り、Job の作成と PDF の保存を1つの処理で行う。PDF の保存に失敗したら Job も作らない（作った Job は同じ処理の中で取消にする）
    - 冪等のかぎは `lineMessageId`（依頼のメッセージの id）。同じかぎで2回目が来たら、1回目の結果（受付番号・保存した PDF の一覧）を返す。2回目の PDF の sha256 と件数が1回目と違えば `INTAKE_MISMATCH` で断る
    - 念のための掃除：`受付` のまま PDF が無い Job が15分続いたら取消にする（既存の秘書室の流れにも効くが、秘書室は受付から PDF の到着まで最大何分かかるかを計画で確かめ、それより長くする）
13. **Webhook の「済み」の境目**：portal から受付番号と PDF の一覧が返り、それが送った PDF と一致した時点で、このイベントを済みにする。その後の返事の失敗では受付を取り消さない
14. **受付の返事**：まず reply で送る。reply が「はっきり失敗」（LINE が 400 番台を返した＝期限切れ・使用済み）のときだけ push で送り直す。通信の失敗など「結果が分からない」ときは送り直さない（二重の返事を避ける）。そのために `sendLineMessage` が「成功・はっきり失敗・不明」を区別して返すようにする
15. **portal の「前の帯替えを処理中」**：エラーの本文に処理中の受付番号 `busyJobNo` を足し、返事に「前の帯替え（#J11）」と書く
16. **返事先の記録**：Job に `replyKind`（`'secretary'`（既定・今まで）か `'line-group'`）と `replyGroupId`（`line-group` のときだけ。`C` で始まる33文字）を足す。portal は受付のときに形を確かめ、**納品の予約（claim）の応答で返す**（一覧ではなく、納品のときの正本の値を使う）
17. **納品は「宛先ごとの状態」を残す**（Mac の LINE秘書）
    - 宛先は2つ：グループ（`replyKind==='line-group'` のとき）と秘書室（いつも）
    - 宛先ごとに `未着手 → 送信中 → 送信済み／はっきり失敗／結果不明` を台帳に残す。送る前に「送信中」を保存し、途中で止まって再開したときに「送信中」のままなら「結果不明」にして送り直さない
    - 送る順番：グループ → 秘書室。グループへは `replyGroupId` が `宛先.json` の「営業部」の ID と完全一致したときだけ送る（一致しなければ送らず「はっきり失敗」）
    - portal への納品結果は今どおり秘書室の送信で決める（秘書室が送信済み＝delivered）。秘書室の控えの文には、グループへの状態を書く：「グループにも送りました」／「グループに送れませんでした」／「グループへの送信結果が分かりません（確かめてください）」
18. **グループあてのリンクの印**：配布トークン（署名の内側）に `aud: 'line-group'` と `g: <groupId>` を入れる。閲覧ページは `aud === 'line-group'` かつ `g === LINE_GROUP_ID`（閲覧ページの環境）が完全一致したときだけ名簿の確認を省く。在籍の確認（`LINE_GROUP_ID` のグループ）は必ず行う。`aud` が無いトークン（今までのもの）は今どおり名簿も見る。`aud` があって値が違う・`g` が違うトークンは拒否
19. **大きい PDF は分けて渡す**（閲覧ページ）
    - 上限：portal の完成品の上限に合わせて **50MiB**（単位は MiB にそろえる）
    - `/api/open` の応答：PDF が 4,000,000 バイト以下なら今どおり全体を返す。それより大きければ「分けて渡す」の案内（全体の大きさ・部分の数・部分の大きさ（3,500,000 バイト）・ファイル名）を返す
    - 部分の取得：`/api/open` に `part=<番号>`（0から、部分の数未満）を付けて同じ確認（トークン・ログイン・在籍・名簿（必要なとき）・失効）を通し、その範囲だけを返す（Drive から範囲を指定して取る）。`Cache-Control: no-store`
    - 閲覧側：全部の部分を順番につなぎ、**全体の sha256 をトークンの値と照合してから** 表示する。合わなければ表示せず「もう一度開いてください」。部分の取得に失敗したら、その部分だけ3回まで取り直す
    - 監査：開いた記録は1回の閲覧につき1件（部分0のときだけ記録）
    - 回数の制限：部分の取得は別の枠（トークンごと・人ごとに 1分あたり 部分の上限数×2）で数える
    - 保存（Safari で開く `/api/dl`）：今回は全体が 4,000,000 バイト以下のときだけ。大きいときは保存の入口を出さず「大きいためこの画面でご覧ください」と出す（分けての保存は次の段で考える）

メッセージの枠：MD NEXT秘書は月5,000通（2026-10-09 時点で使用107通）。グループへの push は人数分（約17通）数えるが十分足りる。受付の返事は reply なので数えない（送り直しの push だけ数える）。

## 流れ
1. 営業部のグループに PDF が出る → aisecretary が帯替え用の控えに足す（9）
2. 下村さんが依頼 → aisecretary が
   1. 入口の確認（6）・依頼の形（7）
   2. 控えから PDF を選ぶ（9）。無ければ断る
   3. LINE から全部取り出す（`api-data.line.me/v2/bot/message/{id}/content`）。1件でもだめならやめる（11）
   4. `POST /api/jobs/intake`（12）。返ってきた PDF の一覧と照合（13）
   5. 受付の返事（14）：「#J12 受付しました（物件：○○／PDF：a.pdf ほか2件）。完成したらここにリンクを出します」
3. portal は今と同じ（自動の下準備 → 自動完成。Discord にも経過）
4. Mac の LINE秘書が完成を見つけて納品（17）。グループに「#J12 帯替えが完成しました（物件名）＋リンク＋要確認のページ数」、秘書室に控え

## 影響する所
### aisecretary（`apps/aisecretary`）
- 新しいモジュール：依頼の判定（`parse` の移植と共通テストデータ）、帯替え用の PDF の控え（KV の sorted set）、portal への送信（`POST /api/jobs/intake`）、受付の処理全体
- Webhook（`src/app/api/webhook/route.ts`）：
  - `source.type` を処理用の値に残す（今は落としている）
  - file メッセージを帯替え用の控えにも足す（営業部のときだけ）
  - 帯替えの分岐を入れる（8）。`export const maxDuration = 60`
  - イベントを済みにする境目（13）
- `src/lib/line.ts`：reply の結果を「成功・はっきり失敗・不明」で返す形を足す（既存の呼び出し元は今の動きのまま）
- 新しい環境変数（Vercel）：`PORTAL_BASE_URL`・`JOB_API_TOKEN`・`JOB_ALLOWED_USER_IDS`。`LINE_GROUP_ID` は既存のものを使う（未設定なら帯替えは止める。既存の機能の既定値の動きは変えない）。**追加は下村さんの承認後、値を画面に出さない方法で入れる**
- 返事に入れるファイル名・物件名は、改行・制御文字を取り、40文字までにする

### portal（`apps/reins-report`）
- 新しい入口 `POST /api/jobs/intake`（12）。鍵は既存の `x-job-token`。中で既存の受付（`createJob` の検査：受付停止・同時1件）と PDF の保存（既存の検査：件数・大きさ・`%PDF-`・sha256 での重複除去）を使う
- Job に `replyKind`・`replyGroupId`（16）。prisma のマイグレーション
- 納品の予約（`/api/jobs/{no}/delivery/claim`）の応答に `replyKind`・`replyGroupId` を足す
- `OBI_BUSY` のエラーに `busyJobNo`（15）
- `受付` のまま PDF が無い Job の掃除（12）
- 既存の `POST /api/jobs`・`POST /api/jobs/{no}/inputs`（秘書室の流れ）は変えない

### Mac の LINE秘書（`apps/line-secretary`）
- `src/jobs/deliver.js`：宛先ごとの状態（17）。グループへの送信は既存の `src/lineapp.js pushText`（宛先「営業部」・`expectId` の照合）
- リンクの発行（`src/dtoken.js`）：グループあてのとき `aud`・`g` を入れる（18）
- 秘書室の控えの文（17）

### 閲覧ページ（`apps/line-secretary/delivery`）
- `lib/dtoken.js`：`aud`・`g` の検査（18）
- `lib/gate.js`：印があるときだけ名簿を省く（18）
- `api/open.js`・`lib/drive.js`・`public/app.js`：分けて渡す（19）
- `api/dl.js`：大きいときは券を出さない（19）

## うまくいかないとき
| 場面 | 返事（グループ） |
|---|---|
| 個別トーク・他のグループ | 帯替えとして扱わない（今までどおりの動き） |
| 設定が足りない・不正 | いま帯替えの受付を止めています |
| 下村さん以外の依頼 | 帯替えの依頼は下村さんからお願いします |
| 直近30分に PDF が無い | 直近30分に PDF がありません。PDF を貼ってからもう一度送ってください |
| 20件を超える・合計25MBを超える | 上限（20件・合計25MB）を書いて断る |
| PDF を1件でも取り出せない・PDF でない | 受付できませんでした（○○.pdf を取り出せません）。貼り直してからもう一度送ってください |
| 前の帯替えを処理中（`OBI_BUSY`） | 前の帯替え（#J11）を処理中です。終わってからもう一度送ってください |
| 受付停止中（`INTAKE_STOPPED`） | いま帯替えの受付を止めています |
| portal に届かない・時間切れ | 受付できませんでした（portal に届きません）。少し待ってからもう一度送ってください |
| 完成リンクをグループに送れない・結果が分からない | 秘書室の控えにその旨を書く（17） |

## 確かめ方
- aisecretary（tsx のテスト）：入口の確認（type・groupId・userId・設定不足）、依頼の形（共通テストデータ）、メール下書き中の優先、PDF の控え（時刻での選び方・20件・依頼より後は使わない・PDF 以外は外す）、取得の失敗で全体中止、portal の各エラー、reply の3つの結果と push の送り直し、済みの境目。LINE・KV・portal は偽物に差し替える
- portal（vitest）：`/api/jobs/intake` の成功・冪等（同じかぎ・中身が違う）・PDF 保存の失敗で Job が残らない・受付停止・同時1件と `busyJobNo`・claim の応答・掃除
- LINE秘書：宛先ごとの状態（グループ成功／失敗／不明 × 秘書室成功／失敗、再開時の「送信中」→不明）、営業部の ID と一致しないと送らない、トークンの `aud`・`g`
- 閲覧ページ：印の有無と値違いでの名簿・拒否、分けて渡す（部分の範囲・番号の検査・つないだ sha256 の照合・合わないと表示しない）、大きいときの保存の入口
- 途中で止まる場面のテスト：intake の途中、Webhook が済みになる前、グループへの送信直後、秘書室への送信直後、部分の取得の途中
- 実地：本番のグループで下村さんが1件依頼し、受付の返事・完成リンク・別の社員がリンクを開けることを確かめる（実在のお客様の資料は使わず、テスト用の図面で）

## 対象外
- 「2番直して」などの番号での直し（次の設計）
- 査定の依頼、PDF 以外の画像の帯替え
- 営業部以外のグループ・個別トークからの依頼
- 大きい PDF の分けての保存（`/api/dl`）
