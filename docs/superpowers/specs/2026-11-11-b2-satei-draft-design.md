# B2 マンションの査定書の下書きをボタンで作る 設計書（2026-11-11・Codex レビュー3回目を反映）

親の設計書：`2026-11-08-button-agent-design.md` 第5節。この文書はその詳細で、食い違えばこちらを正とする。

## 1. 決めたこと（下村さん 2026-11-11）
- 最初の種別は**マンション**だけ
- きっかけは **LINE の案件カードの［査定書を作る］ボタン**
- 組み方は **帯替えと同じ道**（営業支援システム reins-report の依頼箱を使い、Mac の係が作る）
- 下書きと［OK］［差し戻し］は、**秘書の LINE と下村さんの1対1のトーク**に届ける（秘書室は LINE WORKS でボタンが戻らないため。社長には見えない）。押せるのは**下村さんだけ**
- 作るのはテンプレート Excel の正式な査定書（realestate-satei）。reins-report の画面の「簡易査定」は使わない

## 2. 最初の1件の範囲（小さく通す）
入れる：作る → Codex の検品 → 下村さんの［OK］→ 案件フォルダへ写し。版の照合・権限・止まったときの戻り方。
入れない（後の段）：自動の作り直し、［入れたのでもう一度］などの再開ボタン、マンション以外、担当者が自分で押す形。

## 3. 流れ
1. 担当がレインズの成約事例などを案件フォルダの `02_査定・事例` に入れる
2. 案件カードの［査定書を作る］を押す
3. aisecretary：押した人が下村さんか確かめる → CRM_案件 から案件の Notion ID・案件番号（DEAL-####）・「Driveフォルダ」欄を読む → reins-report に `satei` の依頼を作る（第6節の受付 API）
   - 押した場所への返事は「受け付けました。結果は個人の LINE に届きます（J番号）」だけ。案件名・金額は返事に入れない（案件カード自体にはもとから案件名が出ている）
   - 同じ案件で終わっていない `satei` 依頼があれば作らず「作成中です（J番号）」
4. Mac の査定係が依頼を予約して取る（第6節）
5. Drive API で、依頼に付いたフォルダ ID の `01_物件資料`・`02_査定・事例`・`00_案件.md` を読み、**中身ごと** Mac の作業場所に写す（固定写し）。ファイルごとの SHA-256 から「入力の版」を作って依頼箱に記録
6. 材料を確かめる（第8節）。足りなければ作らず依頼を「失敗（材料不足）」で閉じ、個人の LINE へ不足一覧。資料を足したら［査定書を作る］を押し直す（新しい依頼になる）
7. Claude（`claude -p`）が realestate-satei で製本 PDF・編集元 Excel・出典一覧・不足一覧を作る
8. Codex が realestate-satei-check で検品する。自動の作り直しはしない。判定はそのままカードに載せる
9. 査定係が下書き PDF を Drive API で `15_AI納品/年月/査定/J番号_物件名.pdf` に上げ、ファイル ID と SHA-256 を依頼箱へ登録 → 依頼は「確認待ち」
10. 査定係が aisecretary の通知 API を呼び、aisecretary が下村さんへカードを送る：判定・指摘の上位3件・［下書きを見る］（Drive のリンク）［OK］［差し戻し］
   - 通知は依頼箱に「通知待ち → 送信済み／結果不明」として残す。査定係は再起動のたびに「確認待ちで通知が送信済みでない」依頼を探して送り直す
   - LINE への push には `X-Line-Retry-Key`（依頼ごと・世代ごとに固定の値）を付け、送り直しても二重に届かないようにする。結果不明が続いたら（3回）依頼箱の画面に「通知が届いたか不明」と出す
11. ［OK］→ aisecretary が依頼箱の**査定専用の承認 API** を呼び「完成」にする（成果物の SHA-256 と世代を一緒に送り、違えば断る）→ 査定係が案件フォルダへ写しを入れる（第7節）→ 「保存しました」を個人の LINE へ
12. ［差し戻し］→ 「理由を一言返信してください（次の1通を理由として記録します）」→ 依頼は「差し戻し」から「取消」で閉じる。作り直すときは［査定書を作る］を押し直す（理由は次の依頼に引き継いで Claude に渡す）

## 4. 状態（今の Job の状態と表をそのまま使い、新しい遷移は足さない）
| 段 | 状態 | 次 |
|---|---|---|
| ボタンで作った | 受付 | 査定係が予約すると下準備中 |
| 作成・検品中 | 下準備中 | 確認待ち／失敗（材料不足・時間切れ・検品できない） |
| 下村さんの確認 | 確認待ち | 完成（OK）／差し戻し |
| 差し戻し | 差し戻し | 取消（理由を記録して閉じる） |
| OK | 完成 → 納品中 → 納品済み | 「納品」はここでは**案件フォルダへの写し**のこと。入れたか分からなければ納品要確認 |
- 今の jobs.ts の掃除は「inputBatchId が空の下準備中を30分で失敗」にする。`satei` はこの掃除から外し、`satei` 専用に「予約の期限切れ＋60分で失敗」とする
- 1依頼の中でのやり直しは時間切れのときの1回だけ（試行回数を依頼に記録）
  - 予約の期限が切れた「下準備中」の依頼は、査定係が**新しい実行 ID** で取り直せる（試行回数が1回目のときだけ）。取り直した時点で古い実行 ID は無効になり、その結果・延長は断る。2回目も切れたら失敗
- 既存の汎用の状態変更 API（`/api/jobs/[no]/transition` など人の画面・帯替え用）は、`satei` の依頼を動かそうとしたら断る。`satei` は第6節の専用 API だけで動かす
- 既存の deliver.js（完成した帯替えを秘書室へ送る役）は `satei` を拾わないようにする（今の動きは変えない）

## 5. 権限と見え方
- aisecretary の `satei` のボタン（作る・OK・差し戻し）は**すべて**、押した人の userId が `TASK_SATEI_USER_IDS` に入っているか確かめる。タスクの「担当者・依頼者も押せる」決まりは使わない
- `TASK_SATEI` が off のときは案件カードにボタンを出さず、前に出したボタンを押されても「いまは止めています」とだけ返して何もしない
- 依頼箱の鍵（`x-job-token`）は機械どうしの認証で、本人確認ではない。本人確認は aisecretary が行う
- 業務指示グループで押したとき、グループに見えるのは「（ボタン）査定書を作る」と受付の返事だけ。下書き・判定・指摘・金額は個人の LINE にだけ出す
- 同じボタンの二度押し：LINE の webhookEventId を冪等キーにして、2回目は何もしない

## 6. 依頼箱（reins-report）に足すもの
- Job に**案件 ID**（Notion の案件ページ ID）と**フォルダ ID**の列を足す
- **1案件1依頼**：`satei` で終わっていない依頼が同じ案件 ID にあれば作らない。確認と登録は同じトランザクションで、案件 ID ごとに直列にする（Postgres の advisory lock か部分ユニーク索引。どちらにするかは計画で決める）
- 査定係の API（機械用の鍵＋次の値を毎回照合する）：
  - 予約：受付の `satei` を1件取る → 実行 ID・期限（lease）を返す
  - 延長：実行 ID が一致し、期限内のときだけ延ばす
  - 結果：実行 ID・入力の版・成果物の SHA-256・Drive のファイル ID・判定を登録。実行 ID か期限が合わなければ断る（古い係の結果は捨てる）
  - 承認・差し戻し（aisecretary 用）：下村さんの userId（aisecretary が確かめた値）・成果物の SHA-256・世代を受け取り、確認待ちの依頼のときだけ完成／差し戻しにする
  - 保存の予約と完了：完成の依頼を「納品中」にして取り、写しを入れたら保存先 ID と SHA-256 を付けて「納品済み」
  - 保存の中止：保存の予約（実行 ID・期限）が一致するときだけ、理由（入力が変わった／閲覧用が書き換えられた／フォルダ ID が違う）を記録して、納品中→完成→差し戻し→取消 を1つのトランザクションで行う
- 期限が切れたら、査定係は子プロセス（claude・codex）を止める。再起動したら、依頼箱の記録と作業場所を照らし合わせてから続きを決める（10/23 の Codex 試作 `queue.mjs`・`runner.mjs` の考え方を使う）

## 7. 案件フォルダへの写し（OK のあと）
- 書く直前に、Notion の「Driveフォルダ」欄のフォルダ ID と、依頼に記録したフォルダ ID が同じか、もう一度確かめる。違えば書かずに止める
- **順番**（再起動のあとも同じ）：① 保存先に、依頼の成果物と同じ SHA-256 のファイルがもうあるか見る → あれば完了を登録して終わり（入力の照合はしない）② 無ければ下の入力の照合 ③ 書く
- 入力の版を作るとき、このシステムが案件フォルダに入れた査定書（その案件の `satei` 依頼で登録した成果物の SHA-256 と一致するファイル）は数えない。自分で入れた写しを「資料が変わった」と取り違えないため
- 書く直前に、入力をもう一度 Drive から読み、入力の版（ファイルの追加・削除・中身の変更を含む）が依頼の版と同じか確かめる。違えば書かずに、第6節の「保存の中止」で閉じて「資料が変わったので［査定書を作る］を押し直してください」と個人の LINE へ
- 写すのは Mac の作業場所にある、検品した成果物そのもの（SHA-256 が依頼箱の記録と一致するもの）。Drive の閲覧用ファイルを写し元にはしない。閲覧用ファイルが OK の前に書き換えられていないかも、Drive の md5 チェックサムを依頼に記録した値と比べて確かめ、違えば同じく保存しない
- 書くのはそのフォルダの `02_査定・事例` だけ。名前は `物件名_査定書_YYYYMMDD.pdf`
- 同じ名前があるとき：中身の SHA-256 が同じなら「もう入っている」として完了。違えば**上書きせず**止めて下村さんに知らせる
- 書いたあとに Mac が落ちて完了を登録できなかった場合：次に起きたとき、保存先にその SHA-256 のファイルがあれば完了を登録する（二重に書かない）
- 場所は Drive のフォルダ ID で引く。Mac の同期フォルダを名前で探すことはしない（箱の移動・同期の遅れ・別フォルダの取り違えを避ける）

## 8. 材料の確認（作らない条件）
- `02_査定・事例` に成約事例の PDF が1つもない
- 対象物件の種別がマンションと確かめられない。見る順：① CRM_案件 の物件種別の欄（欄の名前は計画の最初に確かめる）② 対象物件の資料（`01_物件資料` の販売図面・物件概要・登記簿の「建物の種類・区分建物」）。①と②が食い違う、またはどちらでも判定できなければ作らない
  - 成約事例（比べるための他の物件）の種目は、対象物件の種別の根拠にしない
  - Drive の決めごとの「種別」（売却／購入など）は取引の種類なので、ここでは使わない
- 所在・専有面積が資料から読めない
- 不足一覧を付けて作るもの：売出事例がない、管理費等が不明、謄本がない など（realestate-satei の決まりどおり）

## 9. 守ること
- 作業場所は Mac の `line-secretary/cases/satei/J番号/実行ID/`（git 管理外）。入力の固定写しと成果物を実行ごとに分ける
- お客様の資料は Grok に渡さない。レインズは触らない。ログには J番号・件数・符号だけ
- 同時に作るのは1件。作成 40 分・検品 20 分で子プロセスを止める
- スイッチ：aisecretary `TASK_SATEI=1`（既定 off。off なら今の動きは1バイトも変わらない）と `TASK_SATEI_USER_IDS`。Mac 側は査定係の launchd を入れない限り動かない

## 10. 作るもの
| 場所 | 中身 |
|---|---|
| aisecretary | 案件カードの［査定書を作る］、CRM_案件 の読み取り（案件番号・Driveフォルダ・物件種別）、依頼箱の受付 API の呼び出し、査定係からの通知 API（機械用の鍵）、個人 LINE へのカード、［OK］［差し戻し］と差し戻し理由の受け取り |
| reins-report | Job の案件 ID・フォルダ ID 列、1案件1依頼、査定係の予約・延長・結果・保存の API、`satei` 専用の掃除、deliver.js 向けの一覧から `satei` を外す |
| line-secretary（Mac） | 査定係（新しい launchd）：予約・延長、Drive API での読み込みと固定写し、材料確認、claude と codex の実行、Drive への下書きの登録、通知、OK 後の写し |

## 11. 試し方と合格
1. 各リポジトリの単体テスト：スイッチ off で今と同じ／下村さん以外が押す／二度押し／同じ案件の連打／古い実行 ID の結果／版の違う OK／同名で中身の違うファイル／写したあとの再起動から完了まで／OK の前に資料を変えたときの保存の中止から取消まで
2. 過去のマンション案件の**試験用の写しフォルダ**（Notion にも試験用の案件を1件）で端から端まで流す
3. 実際のマンション案件1件で、個人の LINE に下書きが届き、検品と下村さんの目視の両方で通ること → 合格
- 本番の前に Codex のレビューで「可」をもらい、下村さんの確認を取る
