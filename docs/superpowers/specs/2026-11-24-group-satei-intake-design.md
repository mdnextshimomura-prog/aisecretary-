# 普通の LINE グループに来た査定の依頼を、査定の流れに乗せる 設計

- 書いた日：2026-11-24
- 状態：**設計（案）**。コードは未着手。作り始め・本番への出し直し（deploy）・設定値（env）の追加は、下村さんの承認後
- 頼んだ人：下村さん（agent-hub のセッション経由）「普通のLINEグループの査定依頼も拾えるようにして」
- 関係する設計：`2026-11-22-photo-mention-ask-design.md`（画像のあとの名指し）、`2026-11-22-satei-ask-card-design.md`（「案件はどれですか」のカード）、`2026-11-11-b2-satei-draft-design.md`（査定書の下書き）、agent-hub `docs/contracts/`（受け口の約束 3本）

この文書で使うことば（最初の1回だけ言い換え）：
- **webhook**（ウェブフック）＝LINE から「発言が届きました」と秘書に知らせが来る入口
- **KV**＝秘書の小さな控え帳（Upstash の Redis）。期限つきでメモを置ける
- **push**＝秘書の側から LINE を送ること。LINE の**月の送信枠**を1通使う
- **postback**（ポストバック）＝カードのボタンが押されたという知らせ
- **カード**＝ボタンつきの LINE の吹き出し（Flex Message）
- **portal の受付（intake）**＝査定書づくりの依頼箱。ここに入ると Mac の査定係が作り始める
- **受付票**＝この設計で新しく作る「1件の査定の依頼」をまとめるメモ（KV に置く）

---

## 1. 目的

業務指示など**普通の LINE グループ**に来た「査定お願いします」を、秘書が見落とさずに拾い、
1. 本文・画像・PDF（登記・地図・チラシ）から物件を読み取り、
2. 下村さんの**個人 LINE（1対1）**で「どの案件か」をボタンで選んでもらい、
3. マンションならそのまま査定書づくりを始め、戸建・土地なら「自動では作れない。手作業に回す」とはっきり知らせる、

ところまでを、秘書（aisecretary）の中だけでつなぐ。

## 2. 範囲

### やること
- グループの発言から「査定の依頼」を見分ける（@AI秘書 の有無を問わない。ただし対象グループを設定で限る）
- 依頼の前後に届いた画像・PDF・返信を**1件の依頼として束ねる**（受付票）
- 束ねた資料を AI（Claude）で読み、**所在（住所・地番）・物件名・種別の見込み**を取り出す。お客様の名前は取り出さない
- 進行中の CRM_案件 から候補を出し、下村さんの1対1にカードを push
- 下村さんが選んだ案件の種別で分ける：マンション→今の査定の受付へ／戸建・土地・不明→手作業の知らせ
- 案件が無い・決まらないときの聞き直し（カードの［一覧から選ぶ］［案件がまだ無い］）
- 決まったことを Notion の LINEタスク に書き戻す（タスクがあるとき）

### やらないこと
- グループへの返事（グループには何も書かない。返事を出すかは未決事項 15-4）
- 案件（CRM_案件）を秘書が作ること（今の決まり「秘書は案件を作らない」のまま）
- 戸建・土地の査定書を自動で作ること（Mac の `src/satei/` はマンション専用。触らない）
- 人のタップなしに査定を始めること（案件の確定は下村さんの1タップ）
- agent-hub（Mac の `bin/hub`）へ渡すこと（理由は 9 節）
- LINE WORKS 側の流れ（line-secretary の hub・`HUB_MODE`）を変えること
- 束ねた画像・PDF を案件の Drive フォルダへ保存すること（未決事項 15-5。今回は「グループにあります」と知らせるだけ）

## 3. 今の流れと、止まった所（大宮の例）

### 3.1 11/23 に起きたこと
| 時刻 | 起きたこと | 秘書の動き |
|---|---|---|
| 11/23 11:55 | 前田社長が業務指示のグループに「査定お願いできますか！」「書類関連お願い致します！」（住所は画像側） | LINEタスク に「物件の査定および書類関連対応」を登録。ステータス＝要確認、物件名＝空、案件の状態＝案件なし、担当＝下村さん。初動確認（足りない条件の聞き返し）で「対象の物件」「売主様のお名前」「査定の前提」を要指示にした |
| その後 | 山口さんが同じグループに登記PDFを返信 | 何もしない（頼みごとでない発言は残さない作り。PDF は山口さんの控えに入るだけ） |
| 同日 | 下村さんが手作業でスキルを使って査定書を作り、送付 | — |

Notion のページ（`421fd849-2778-8198-80ac-cc37b018c68a`）で確かめた事実：`メッセージID` が3つ、`発生元` は業務指示のグループ、`依頼者` は前田社長、`担当者` は下村さん、`物件名`・`物件キー` は空。

### 3.2 止まった所（4か所）
1. **画像を読めていない**：物件名が空なので、AI に住所の画像が届かなかったか、届いても物件として取れなかった。どちらかは**未確認**（ログに画像の ID を出さない作りのため）。今の作りは「@AI秘書 の**直前**に、**同じ人**が送った画像」だけを読む（`media.ts`）。画像が依頼文の**後**に来ると読まれない。
2. **別の人の資料をつなげない**：控え（`emailmedia:<グループ>:<送り主>`）は**送り主ごと**。山口さんの登記PDFは前田社長の依頼と結び付かない。
3. **タスクと査定の流れがつながっていない**：LINEタスク の「種別：査定書」は期日を決めるためにだけ使われ、査定の入口（案件カードの［査定書を作る］）へは何も渡さない。
4. **入口が案件カードしか無く、そのカードも絞られている**：［査定書を作る］は案件カード（グループの「@秘書 案件」）にしか無く、そのカードは `ONLY_DEAL_IDS`（試しの絞り込み。DEAL-238・239 だけ）で絞られている。さらに大宮は戸建なので、押せても「いまはマンションの案件だけ作れます」で止まる。

## 4. 新しい流れ（全体）

```
グループの発言（文字・画像・ファイル）
  │ webhook
  ▼
① 受け取り：対象グループなら、画像・ファイルはグループ単位の控えにも記録（中身は持たない）
  ▼
② 依頼の判定：査定の依頼か？（入口は3つ。6節）
  │  はい → 受付票を作る（同じ依頼で二重に作らない）
  ▼
③ 資料を束ねる：依頼者本人の前後の画像・PDF／引用リプライ／（条件つきで）他の人の資料
  ▼
④ 読み取り：Claude で所在・物件名・種別の見込みを読む（お客様の名前は捨てる）
  ▼
⑤ 候補：進行中の CRM_案件 と照らし、最大5件
  ▼
⑥ 下村さんの1対1にカードを push（候補／一覧から選ぶ／案件がまだ無い／査定ではない）
  │  後から資料が来たら③④をやり直し、カードを出し直す（最大2回）
  ▼
⑦ 下村さんがタップ＝案件の確定
  ▼
⑧ 種別で分ける（CRM_物件 の `種別` が正）
  ├ マンション＋フォルダあり → portal の受付（今の［査定書を作る］と同じ）→「受け付けました（#J12）」
  ├ マンション＋フォルダなし → 「案件の Driveフォルダが未設定です」
  ├ 戸建・土地 → 「戸建のため自動作成はできません。手作業の査定に回します」
  └ 種別が不明・案件がまだ無い → 「手作業の査定に回します」＋理由
  ▼
⑨ LINEタスク に書き戻す（案件・状態）。グループには何も返さない
```

## 5. 受け取り（①）

- スイッチ `GROUP_SATEI=1`（既定 off）、対象は `GROUP_SATEI_GROUP_IDS`（カンマ区切り。空なら何もしない）。off のあいだは KV も読まず、今の動きを1バイトも変えない。
- 対象グループの**画像・ファイル**が届いたら、今までの控え（`emailmedia`）に加えて、**グループ単位の控え** `gsatei:media:<groupId>` に1行足す：`{messageId, kind: "image"|"pdf"|"other", senderId, at, quoted?}`。
  - ファイル名は**持たない**（「坂本様_登記.pdf」のようにお客様の名前が入るため）。PDF かどうかだけ `kind` に残す。
  - 最大30件・期限3時間。中身（画像そのもの）は持たない（読むときに LINE から取り直す）。
- 文字の発言は控えない（受付票がある依頼への引用リプライだけ、受付票に足す。7節）。

## 6. 依頼の判定（②）

### 6.1 入口（3つ。どれか1つで受付票を作る）
| 入口 | 条件 | AI の呼び出し |
|---|---|---|
| A. @AI秘書 あての依頼 | 今の登録の流れで `requestType === "査定書"` になった（登録の成否は問わない） | 増えない（今の判定の結果を使う） |
| B. メンションの無い依頼 | 対象グループ・送り主が下村さん以外・本文が「査定」「価格を出して」「いくらで売れ」「売却価格」「相場」のどれかを含む → `parseTaskFromMessage` で `isTask` かつ `requestType === "査定書"`・確信度0.5以上 | 1回（言葉で絞ってから呼ぶので回数は少ない） |
| C. 画像のあとの「@下村」だけ | 今の `photo-ask` の条件（20字以内・下村さんへの mention・画像あり） | 1回（今の photo-ask の代わり） |

- 「査定書を送りました」「査定ありがとうございます」のような**報告・お礼**は、言葉の絞り込みでは通るが AI の判定（`isTask`）で落とす。
- 送り主が下村さん本人の発言は入口にしない（自分で動ける・自分あての知らせを作らない）。
- 入口 C は photo-ask と重なるので、`GROUP_SATEI` が on かつ対象グループのときは、photo-ask は**動かない**（受付票の流れが代わりに知らせる）。対象外のグループでは photo-ask は今のまま。二重の知らせを防ぐため、予約の鍵（画像の ID の組）を両方で共有する。

### 6.2 受付票
- 置き場：`gsatei:t:<ticketId>`（期限7日）。`ticketId` は入口の発言の ID の SHA-256 の16進先頭16字（同じ発言では同じ値＝二重に作らない。SET NX。英数字だけなので portal の依頼の ID の形 `/^[0-9A-Za-z]{10,64}$/` にも収まる）。
- 受付番号：`G7` のような通し番号（KV の `gsatei:seq` で振る）。カード・ログで受付票を指す名前に使う。
- 中身：`{no, ver, groupId, requesterId, at, triggerMsgIds[], mediaIds[], notionTaskId?, read?: {所在, 物件名, 種別の見込み, 根拠, 確信度}, state, dealId?, jobNo?}`。
  - **本文・お客様の名前・ファイル名は入れない**。`read` の所在・物件名は残す（物件の情報。下村さんのカードと LINEタスク にだけ使う）。
  - `state`：`asking`（カードを出した）→ `started`（査定を受け付けた）／`manual`（手作業へ）／`dismissed`（査定ではない）／`expired`（7日で閉じた）。
- グループごとの「開いている受付票」の目次 `gsatei:open:<groupId>`（集合。`asking` のものだけ）。
- 発言の ID → 受付票の引き `gsatei:msg:<messageId>`（期限7日）。入口の発言・束ねた画像の ID を全部入れる（引用リプライでたどるため）。

## 7. 資料を束ねる（③）

Codex の確認（11/24）を受けて、「時間内なら誰の資料でも足す」はやめ、**結び付きが確かなものから**足す。

| 優先 | どの資料を足すか | 根拠 |
|---|---|---|
| 1 | 依頼者本人の画像・PDF で、入口の発言の**30分前〜60分後** | 社長の依頼は「画像→ひと言」「ひと言→画像」のどちらもある |
| 2 | 誰の発言でも、受付票の発言・画像を**引用リプライ**したもの（画像・PDF・文字） | 山口さんの登記PDFがこの形なら確実につながる |
| 3 | 引用の無い他の人の画像・PDFで、入口の発言から**2時間以内**、かつそのグループで開いている受付票が**1件だけ** | 「仮に足す」。読み取りで所在が受付票と食い違えば外し、カードに「別件の可能性がある資料を除きました」と書く |

- 1件の受付票に足す資料は最大8件（画像・PDF 合わせて）。超えた分は読まず、カードに「資料が多いため一部だけ読みました」。
- 受付票が `started`／`manual` になった後に来た資料は、読み直さず、下村さんに「〈受付票〉に追加の資料が届きました（グループで確かめてください）」の1行だけ送る（1受付票につき1日1回まで）。査定のやり直しは黙って始めない。
- **大宮の例で山口さんの PDF が引用リプライだったかは未確認**。引用でなければ優先3（受付票が1件だけ・2時間以内）で拾える見込み。

## 8. 読み取り・候補・カード（④〜⑦）

### 8.1 読み取り（④）
- いつ：受付票を作ったとき（その時点の資料で）。後から資料が足されたら**読み直す**（最大2回・前回から2分以上あける）。Codex 案 A（その場で読む＋後から足す）を採用。毎分の見回り（cloud-tick）に相乗りして「静かになってから読む」案 B は、30分後に来る登記PDFを待てないので採らない。
- 何で：Claude（今と同じ Anthropic の API・同じモデル）。**新しい読み取り用の指示文**を1つ作る（今の `parseTaskFromMessage` は種別の見込みを返さないため）。返す形は JSON：
  - `所在`（住居表示か地番。例「大阪市旭区大宮1丁目3番27」）
  - `物件名`（マンション名＋号室。無ければ null）
  - `種別の見込み`：`マンション`／`戸建`／`土地`／`不明`（登記の「区分建物」「居宅」「宅地」などから）
  - `根拠`：`本文`／`登記`／`地図`／`チラシ`／`その他`
  - `確信度`（0〜1）
- 指示文で「所有者・人の名前は出さない」と指示し、さらにコードで、`様`・`邸`・`さん`・`氏`・`所有者`・`持分` を含む行を捨てる（photo-ask・satei-ask と同じ守り）。
- 時間の上限：画像1枚8秒・AI 40秒（photo-ask と同じ）。webhook の中で読む（同じ webhook の次の発言の処理が最大約1分遅れうる。今の photo-ask・候補と同じ扱い）。

### 8.2 候補（⑤）
- 読んだ `物件名` と `所在` を、それぞれ `normalizeProperty` でそろえて `candidateDeals`（完全一致→部分一致、最大5件）。両方の候補を合わせて重複を除く。
- 1件だけ当たっても**確定しない**（ボタンを出すだけ）。今の決まりのまま。
- 案件の一覧は `loadActiveDeals`（進行中の全件）を直接使う。**`ONLY_DEAL_IDS` は通らない**（10節）。
- CRM_物件 の住所の欄で照らせるかは**未確認**（欄があるか確かめていない）。今回は案件名だけで照らす。

### 8.3 下村さんへのカード（⑥）
1対1に push（月の送信枠を1通。読み直しで出し直すたびに1通）。`X-Line-Retry-Key` は `uuidv5(ticketId:ver)` で二重を防ぐ。

**文字（1通目）の例：大宮**
```
🏠 業務指示のグループで査定の依頼がありました
11/23 11:55・前田さん（受付 G7）
読み取った物件：大阪市旭区大宮1丁目3番27
種別の見込み：戸建（登記から）
資料：画像2枚・PDF1件（山口さんの返信を含む）
どの案件か選んでください。
```

**カード（2通目）**
```
［大宮1丁目 戸建 で進める］      ← 候補（最大5件。案件名とフェーズを並べる）
［一覧から選ぶ］                  ← 進行中の案件を10件ずつ
［案件がまだ無い（手作業で査定）］
［査定の依頼ではない］
```
- マンションの候補のボタンは［〇〇で査定書を作る］、戸建・土地の候補は［〇〇で進める（手作業）］と、**押す前に結果が分かる言葉**にする（Codex の指摘：1タップで受付まで進めるなら、ボタンの言葉で開始の意思をはっきりさせる）。ボタンの言葉の種別は CRM_物件 の `種別`（カードを作る時に読む）。読めなければ［〇〇で進める］。
- 確信度が0.7未満なら1行目を「査定の依頼かもしれません」にする。
- 読めなかった（画像が取れない・時間切れ・AI の失敗）ときも黙らず、「資料を読めませんでした。グループで確かめてください」＋［一覧から選ぶ］［案件がまだ無い］［査定の依頼ではない］を送る。
- 押せるのは `TASK_SATEI_USER_IDS` の人だけ（今の査定のボタンと同じ）。

**ボタンの data（postback）**
| ボタン | data |
|---|---|
| 候補・一覧の［〇〇で…］ | `v1|gs|<ticketId>|<ver>|<案件ID>` |
| ［一覧から選ぶ］ | `v1|gl|<ticketId>|<ver>|<オフセット>` |
| ［案件がまだ無い］ | `v1|gm|<ticketId>|<ver>` |
| ［査定の依頼ではない］ | `v1|gn|<ticketId>|<ver>` |

- `ver` が受付票の今の版と違えば「新しいカードが届いています。そちらから選んでください」（古いカードからの押し間違いを防ぐ）。
- 二度押し・LINE の再送は、今と同じ `pb:<webhookEventId>` の予約で止める。決めるのは**受付票ごとに最初の1回だけ**（SET NX）。2回目以降は「選択済みです（〇〇）」。
- 例外は［案件がまだ無い］だけ：これは仮の決定とし、7日以内なら同じカードの［一覧から選ぶ］で案件を1回だけ選び直せる（CRM_案件 を後から作る場合のため）。選び直した後は上と同じく最初の1回で固定。
- portal の受付に渡す依頼の ID は、受付票から作る決まった値（`gs` ＋ ticketId の形。portal の `eventId` の形に合わせる）にし、同じ受付票から2回受付を作らない。
- 既存の `v1|sa|`（案件カード）・`v1|qa|`（Mac 向けのカード）の意味は変えない。

### 8.4 案件の確定と、種別での分岐（⑦⑧）
下村さんのタップ＝案件の確定。そのまま次へ進む（Codex：ボタンの言葉で結果が分かれば1タップでよい）。

| 状況 | すること | 下村さんへの返事（その場の返事。送信枠を使わない） |

| マンション・フォルダあり | 今の［査定書を作る］と同じ確かめ方で portal の受付 | 「受け付けました。結果は個人の LINE に届きます（#J12）」（今と同じ文） |

| 土地 | 同上 | 「土地のため自動作成はできません。手作業の査定に回します」 |

- **種別の正は CRM_物件 の `種別`**。AI の見込みと食い違ったら（例：CRM はマンション、登記は居宅）、返事に「資料からは戸建に見えます。CRM_物件 の種別を確かめてください」を1行足す。自動の判断は CRM に従う（今の `judgeSateiDeal` を変えない）。

### 8.5 LINEタスク への書き戻し（⑨）

## 9. agent-hub へ渡すか

**結論：渡さない（今回の範囲では不要）。** Codex も同じ結論（11/24）。

理由：
1. agent-hub は「決まった形の依頼を確かめて、今ある係へ渡す受け口」（Mac 上の `bin/hub`）。査定の渡し先（`routes.toml` の satei）は最後に aisecretary の `POST /api/satei/request` を呼ぶ。グループの依頼はもともと aisecretary に届いているので、hub を通すと「Vercel → Mac → aisecretary」と遠回りになり、Mac が止まっていると進まない。
2. `/api/satei/request` は**機械からの自動開始**の口（`machine:true`。差し戻しの続きは受けない・1日3件などの上限）。この設計は下村さんのタップで始める「人の受付」なので、今の［査定書を作る］と同じ道（portal の受付を直接）を使うのが正しい。
3. 渡すと、お客様の資料に近い情報（所在など）を Mac・hub・Grok Bot の側に出すことになる。photo-ask の決め事「Grok Bot・受け口（agent-hub）へ渡さない」に合わない。
4. 戸建・土地は hub に渡しても作れる係が無い。

将来、Grok Bot から「今日の査定の依頼は？」を見たくなったら、そのとき「受付票の件数と受付番号だけ」を返す読み取りの口を別に考える（今回は作らない）。
なお、hub の「要確認の知らせ」（`POST /api/satei/ask/review`）は LINE WORKS 側の話で、この設計とは独立。こちらが先に出ても、あちらの作り始めの承認には影響しない。

## 10. ONLY_DEAL_IDS（試しの絞り込み）の扱い

**事実**：`ONLY_DEAL_IDS` を使っているのは、グループの［案件］のカード（`deal-card-wire.ts` の `loadDeals`）だけ。photo-ask・satei-ask・この設計の候補と［一覧から選ぶ］は `loadActiveDeals` を直接使うので**絞り込みの影響を受けない**。つまり、この設計を動かすだけなら `ONLY_DEAL_IDS` は変えなくてよい。

選択肢（決めるのは下村さん。どれも本番の出し直しが要る。A を除く）：
| 案 | 中身 | 利点 | 欠点 |
|---|---|---|---|
| A. そのまま | 今の2件のまま | 出し直し不要。新しい流れは1対1なので困らない | グループの［案件］から［査定書を作る］を押せる案件は2件のまま。案件カードの試しが終わったか曖昧なまま残る |
| B. 外す（`[]` に戻す） | 進行中の全案件を出す | 本来の形。グループからも全案件で［査定書を作る］（押せるのは下村さんだけ） | 業務指示などのグループで、全員に全案件の名前・フェーズが見える（今も「@秘書 案件」で見える設計だが、試しでは2件に限っていた）。出し直しが要る |
| C. 案件を足す | 必要な案件を都度足す | 見える範囲を小さく保てる | 足すたびに出し直し。運用が回らない |
| D. 設定値に移す | `DEAL_CARD_ONLY_IDS`（env）に移し、コードからは外す | 以後は出し直しなしで Vercel の設定だけで変えられる | 一度は出し直しが要る。設定の取り違えに気づきにくい |

**推奨：A（今はそのまま）。** 次にコードを出し直すとき（この設計の1段目）に、D を一緒に入れて、中身は今と同じ2件で始める。外す（B）かは、案件カードの試し（DEAL-238・239）が終わったと下村さんが判断した時点で、設定だけで切り替える。

## 11. 費用とプライバシー

### 11.1 費用（AI の画像読み取り）
- 1件の受付票で、最初の読み取り1回＋読み直し最大2回＝**最大3回**。1回で画像3枚＋PDF 数ページ程度。
- 概算：1回 1〜2万トークン（画像1枚 約1,500、PDF 1ページ 約2,000〜3,000）×今のモデルの単価で、**1回あたり数円〜十数円、1件で最大40円程度**の見込み（**概算・未実測**。単価は作るときに確かめる）。
- 入口 B は言葉で絞ってから AI を呼ぶので、雑談で AI は呼ばない。
- 歯止め：1日の読み取りは20回まで（KV で数える。超えたら読まずに「資料を読めませんでした（本日の上限）」のカード）。Anthropic の月の上限（$30・会社カード）は今のまま。月の使用量の見方は `docs/運用.md` に足す。
- LINE の送信枠：1件につき通常1〜2通（カード＋読み直し／朝の催促）。月の枠の大きさは**未確認**（契約のプランを確かめていない）。

### 11.2 プライバシー（お客様の名前・登記を外に出さない）
- 画像・PDF を渡す先は **Anthropic（Claude）だけ**。今の @AI秘書 の画像つき受付・photo-ask と同じ扱い（11/22 の判断：「外に出さない」は Grok Bot・agent-hub へ渡さないこと）。**Claude にも渡さない方がよいなら、読み取りをやめて「画像つきの査定の依頼がありました」の固定文＋［一覧から選ぶ］だけにする**（未決事項 15-1）。
- KV に置くのは、ID・時刻・種別・所在・物件名だけ。本文・ファイル名・所有者名・画像の中身は置かない。
- AI の答えからは、名前らしい行をコードで捨てる（8.1）。カード・LINEタスク にもお客様の名前は出さない。
- ログは符号だけ：`[group-satei] ticket G7 opened|read ok|read failed|asked 3|gs started #J12|gs manual|gn dismissed|skip:<理由>`。本文・所在・物件名・userId・groupId・案件名は出さない。
- グループには何も返さない（グループの他の人に、査定の対象や結果を見せない）。
