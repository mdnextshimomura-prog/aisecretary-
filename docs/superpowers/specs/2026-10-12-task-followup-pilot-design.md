# タスクの追いかけ（入口と出口の作り直し）— 試行の設計

- 日付: 2026-10-12
- 対象: `apps/aisecretary`（会社のグループ LINE の秘書）と Notion「LINEタスク」
- 状態: 設計。下村さんの確認待ち
- 経緯: LINE WORKS 秘書の AI 停止（API 残高切れ）の調査から、タスク機能全体の見直しに発展した。Codex に設計レビューを依頼し、「直してから進める」の判定を受けて順番を組み替えた

## 1. 目的

1. LINE で流れてくるタスクを Notion に集め、本人の見落としを減らす。
2. 本人が見落としても、管理職が Notion を見て「これどうなってる？」と聞ける状態にする。

この 2 つが成り立つ条件は、**台帳が実際の仕事と合っていること**。画面や通知はその後に付いてくる。

## 2. いま起きていること（2026-10-12 実測）

| 事実 | 中身 |
|---|---|
| 入口が止まっている | 登録数は 7月 71 → 8月 75 → 9月 15 → 10月 0。最後の登録は 9/4。9/4 は「秘書へのメンション付きだけ受け付ける」に変えた日（`2879dd2`） |
| 変えた理由 | メンション不要のころ、全部の発言が登録されて台帳が荒れた（下村さん談） |
| 出口が無い | 棚卸しで残っていた未完了 15 件のうち、12 件は実際には終わっていた。仕事ではなく記録が止まっていた |
| 8月の実測 | 109 件登録・完了 1 件・期限超過 103 件。完了の操作（引用リプライ・番号返信）を足しても使われなかった |

台帳を見ても今の仕事は分からない。管理職の画面を先に作ると、「止まっている」と出るものの大半が空振りになり、信用されなくなる。

## 3. 進め方

| 順 | 内容 | この設計書の範囲 |

| 2 | 少数の人で、入口・出口・管理職の画面・案件のひも付けを一式試す | **ここ** |

土台は今の秘書と「LINEタスク」をそのまま使う（作り直さない）。

## 4. 入口：登録と「候補」を分ける

| 発言 | 扱い |
|---|---|
| 秘書へのメンション付きで、確信度 0.7 以上の依頼 | 今までどおり、すぐ登録する |
| 秘書へのメンション付きで、確信度 0.7 未満 | 捨てずに「候補」にする |
| メンションなしで、依頼に見える発言 | 「候補」にする |
| 雑談・連絡・相槌 | 何もしない |

### 候補

- 台帳（Notion）には入れない。KV に控える。リマインドにも管理職の画面にも出さない。
- 1 日 1 回、秘書が LINE でまとめて聞く。

  ```
  タスクにしますか？
  1. ○○様へ見積を送る（△△さんあて）
  2. □□マンションの鍵を返す
  「1 登録」「2 いらない」と返してください
  ```

- 「登録」と返したものだけ、通常の登録の流れ（担当・期日の確定、二重登録の防止）に乗せる。
- 答える人は、依頼された本人。あて先が分からない候補は下村さんに聞く。
- 3 営業日返事がなければ消す。消した件数だけ記録する（中身は残さない）。
- 番号は、完了用の番号（リマインド番号）と取り違えないよう、文法を分ける（「1 登録」「1 いらない」。完了は「3済」）。

### メンションなしの発言のふるい分け

- 安いモデル（Haiku）で「依頼かどうか」だけを見る。依頼に見えたものだけ、今の解析（Sonnet）に渡して題名・担当・期日・物件名を取り出す。
- 画像・ファイルだけの発言、帯替えの依頼、メール指示、秘書のコマンドは対象外（今の振り分けの後ろに置く）。
- 費用は試行中に実測する。月 40 ドルの枠（下村さんの希望）に収まらないなら、対象のグループを絞るか、ふるい分けの条件を厳しくする。

### 電話・口頭で決まったこと

新しい仕組みは作らない。「@AI秘書 橋本さん 金曜までに○○」と一言送れば、今の登録の流れで入る。足すのは **依頼者の記録** だけ。誰が記録するかは、その会話で決める（運用の決めごと）。

## 5. 出口：LINE から一言で状況を返す

今の「3済」を広げる。番号は、秘書から届いた知らせの番号。

| 返し方の例 | 台帳に起きること |
|---|---|
| `3済` | ステータス＝完了、終わり方＝完了 |
| `3待ち 売主の書類 金曜` | ステータス＝進行中、状況＝「売主の書類」、次に確認する日＝次の金曜 |
| `3延期 10/20` | 期日＝10/20 |
| `3不要` | ステータス＝完了、終わり方＝不要（ページは消さない） |

- 「待ち」の日付は省ける。省いたら 3 営業日後にする。
- 引用リプライでも同じ言葉が使える（今の「完了」「取り消し」に追加）。
- 今の「取り消し」（ページを消す）は残す。登録の間違いを消す用途に限る。

### 知らせ方を変える

今は毎朝、未完了を全部並べている。これが読まれなくなった原因と見る。

- 朝に出すのは次の 3 つだけ：前日から新しく入ったもの／次に確認する日が来たもの／期限を過ぎたもの。
- 「待ち」と返したものは、次に確認する日まで出さない。
- 人ごとにまとめる。1 人あたりの件数が多いときは上位だけ出し、残りは件数とダッシュボードへのリンクにする。期限を過ぎた重要なもの（緊急度＝今日中）は省かない。
- 番号での返信は、期日が先のものにも効くようにする（今は「期日が明日まで」に限られていて、番号を返しても「見つかりません」になる穴がある）。

## 6. 台帳に足す欄

既存の欄は、型も名前も変えない（リマインド・番号完了・負荷集計が欄の名前と型に依存しているため）。足すだけ。

**LINEタスク**

| 欄 | 型 | 中身 |
|---|---|---|
| 状況 | テキスト | 待ち相手・理由のひとこと |
| 次に確認する日 | 日付 | この日までは知らせない |
| 終わり方 | セレクト | 完了／不要／重複 |
| 依頼者 | テキスト | 頼んだ人（名簿の氏名） |
| 依頼者ID | テキスト | 頼んだ人の LINE userId |
| 発生元 | テキスト | 発言の来たグループの ID |
| 担当（ユーザー） | ユーザー | Notion のユーザー。今の「担当者」（セレクト）は併記で残し、秘書の処理は今までどおりセレクトを正とする |
| 案件 | リレーション | CRM_案件 へ。案件側には「タスク」として出る |
| 案件の状態 | セレクト | 確定／候補あり／未割当／案件なし |

**メンバー名簿**：「Notion ユーザー」（ユーザー型）。LINE の人と Notion の人の対応表。未登録の人は空。

**CRM_案件**：この試行では欄を足さない（「LINE トーク」の欄は、案件専用のグループが実際に必要になってから）。歩合・週報に使う欄と、フェーズには一切書き込まない。

欄は **Notion 側に先に作ってから** コードを反映する（無い欄に書くと登録が丸ごと失敗する。8 月に同じ理由で朝のリマインドが 6 日止まった）。

## 7. 案件へのひも付け（試行では控えめに）

Codex の指摘どおり、「1 件だけ当たったら確定」は使わない（同じ建物の別の部屋、売却と購入、同じお客様の別取引で間違う）。

1. タスクの物件キー（今ある正規化）を、進行中の案件（フェーズが完了・失注以外）の名前に照らす。
2. 正規化した名前が **完全に一致** する案件が 1 件だけ → 「案件」に入れ、状態は「候補あり」（確定ではない）。
3. 部分一致・複数 → 「案件」は空のまま、状態は「候補あり」。候補の案件名をページ本文に残す。
4. 当たらない → 「未割当」。物件名の無いタスク → 「案件なし」。
5. 「確定」にするのは人（管理職の画面で、案件を選んで状態を変える）。

決まり：秘書は案件を新しく作らない。ひも付けに失敗してもタスクは必ず登録する。案件の一覧はメモリに数分キャッシュする。CRM_案件の重複（実重複 5 組）は週報側の作業で整理中なので、試行の間は「候補あり」止まりにして影響を受けないようにする。

前提の確認（未確認・実装の最初に確かめる）：秘書の Notion 連携が CRM_案件 を読めるか（トークンが 2 系統ある）。ユーザー型の欄に書くための権限があるか。読めない・書けない場合、その欄は空のままにして他は進める。

## 8. 管理職の画面（Notion）

「LINEタスク」の見え方を 1 ページにまとめる。新しいデータベースは作らない。

| 一覧 | 条件 |
|---|---|
| 期限切れ | 未完了で、期日が過ぎた（人別） |
| 確認する日を過ぎた | 未完了で、次に確認する日が過ぎた |
| 状況が分からない | 未着手のまま、登録から 3 営業日以上、状況が空 |
| 待ち | 進行中で、状況が入っている（理由と確認日が見える） |
| 案件が決まっていない | 案件の状態が「候補あり」「未割当」 |

「何日も更新されていない」は条件に使わない（秘書や管理者の編集でも更新日時が動くため）。

管理職が聞いた結果は、本人が LINE で「3待ち …」「3済」と返すか、管理職がその場で「状況」と「次に確認する日」を書く。聞いた後に台帳へ戻らないと、同じ確認が繰り返される。

## 10. 壊さないための決まり

- 枝は本番の `integration/email-and-media` から切る。反映は同じツリーから、下村さんの承認を得て行う。GitHub は公開設定のため push しない。
- Webhook の先頭にある帯替えの振り分けの順番は変えない。`tests/obi-*webhook*.test.ts` を通す。
- 営業部のグループでは、引用つきの「数字だけ」「OK」「9」の返信を、帯替えの訂正・差し戻しの枝が先に確かめている。新しい返し方（「1 登録」「1 いらない」「3待ち …」「3延期 …」「3不要」）は、数字だけの形にしない。帯替えの共通の表 `tests/fixtures/job-command-cases.json` の全行で、帯替え側の読みが変わらないことをテストで固定する。
- Notion の欄の追加は事前承認が要る（統合ハブの決裁）。足す欄の一覧（6 章）を見せて承認を得てから作る。
- LINE の再送は本番で無効。新しい処理は「1 回で終える。失敗したら返信で知らせる」前提で作る。
- 登録の入口は 3 つある（通常／聞き返しメニュー経由／API 停止時の控え）。足した欄は 3 つすべてに効かせる。
- 今回さわる所（Notion への書き込み、名簿、リマインド）にはテストが無い。先にテストを足してから変える。
- 候補の機能と新しい知らせ方は、環境変数のスイッチで切れるようにする。切れば今の動き（メンション必須・毎朝の全件リマインド）に戻る。
- 秘書の登録失敗・通知失敗は、今ある「API が止まったら LINE で知らせる」仕組みに乗せる。

- 個人あての通知（1 対 1 のトーク）。試行ではグループへの通知のまま、書き方を事実と必要な行動に絞る。

## 13. 実装で設計から変えた点（2026-10-12）

- 候補への返事は「1 登録」「2 なし」。「いらない」「不要」はタスクの番号の言葉（「3不要」）と重なるので、候補では使わない。
- 「登録」は 1 件ずつ（登録の返信を 1 件ごとに出すため）。「なし」はまとめて返せる。
- メンションなしの発言のふるい分けは、安いモデルではなく、依頼の言い回しの一覧（正規表現）で行う。通ったものだけ、今のタスク解析に 1 回渡す。
- 候補を控えるのは会社グループの発言だけ。聞くのも会社グループ。「@AI秘書 候補」でいつでも一覧を出せる。
- 返事の無い候補を消すまでは 5 日（暦日）。
- 朝のリマインドの件数の打ち切りは入れない（全件を出す過去の判断を優先）。「待ち」の既定の確認日は 3 日後（休業日なら翌営業日）。
- 既知の弱い点：候補から登録したタスクの担当者は AI の読みのまま（名簿での正規化・自動割当を通らない。聞き返しメニュー経由の登録と同じ穴）。記録とひも付けの段で直す。
- コードレビュー（10/12）で直した点：理由に「決済」「完了」を含む「待ち」が完了として読まれる不具合（番号つき・引用リプライとも。処理の順を直した）。「待ち合わせ…」を待ちと読む取り違え（後ろは空白か文末に限る）。候補への返事を会社グループの中だけに限る。候補は登録できてから消す。担当と依頼日を登録に引き継ぐ。一覧を出し直しても番号を変えない。17 時の聞き取りは 17 時台の 1 時間の幅で受ける。
- 残した点（試行で様子を見る）：同時に 2 件届いたときに候補の片方が消えうる（KV の一覧を丸ごと読み書きするため）。休業日にも 17 時の聞き取りが出る。延期で過ぎた月日を書くと翌年になる（返信に年は出ない）。
