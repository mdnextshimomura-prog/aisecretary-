## 3. ファイル別の詳細

### 3-1. `src/app/api/webhook/route.ts` — 最大の衝突点（両側で大改造・335行差）

分岐の判定順序がまったく違う。

**ローカル（現本番）の順序**
```
署名検証 → 番号完了判定（「3済」）→ 引用リプライ（取消/完了/担当者）
→ #新規 → Claudeタスク判定 → due-rules で期日確定 → Notion起票
```

**origin/main の順序**
```
署名検証 → 画像メッセージ→名刺/メディア退避 → ファイル(PDF)→添付候補退避
→ メール下書きセッションがあれば最優先で確認応答 → 引用リプライ（取消/担当者）
→ 曖昧確認への返答 → #新規 → 確定メール指示 → intent判定（曖昧なら確認メニュー）
→ Claudeタスク判定 → Notion起票
```

- ローカルにしか無い: 番号完了 (`parseNumberedCompletion` 判定ロジック・誤爆防止の残差判定)、完了意図判定 (`isCompleteIntent`＋否定語ガード)、`resolveDue` 呼び出し
- origin にしか無い: `image`/`file` メッセージの処理（ローカルは `type !== "text"` で捨てている）、メールセッション最優先分岐、曖昧確認、`registerTaskFromText` / `registerCrmFromText`
- **統合は手作業必須。** 機械マージでは順序が壊れる（メール確認セッションと番号完了判定はどちらも「最優先」を主張する）

### 3-3. `src/lib/claude.ts` — 期日ロジックが真っ向から対立

- **origin版**: プロンプト内の日本語で期日を推測させる旧方式（「査定書→1週間後」「資料→午前当日/午後翌日」…）。`due-rules.ts` を作った動機そのもの（同じ依頼でも実行のたび期日が変わる非決定性）が残っている。
- **ローカル版**: `requestType`（8種）と `urgentHint` だけ判定させ、日付計算はコード側。`REQUEST_TYPES` 外の値は「その他」に丸めるフォールバック付き。
- **ローカル版を採用一択。** ただし origin の webhook は `parsed.requestType` を一切見ないので、統合時に webhook 側の期日確定ブロックを移植し忘れると**期日が空のまま起票される**。

### 3-4. `src/lib/remind.ts` — origin版には修正済みバグが残っている

origin版:
```js
const todayTasks   = tasks.filter((t) => t.dueDate === todayStr);
const tomorrowTasks = tasks.filter((t) => t.dueDate !== todayStr);
```
期日が時刻付き（`2026-08-02T15:00:00+09:00`）だと `"2026-08-02"` と一致せず、**本日期限が「明日期限」に化ける**既知バグ。ローカル版は `dueDateOnly()` で日付だけ比較して修正済み。
加えて origin版には 期限超過セクション・番号採番 (`setRemindNumber`)・表示件数制限が無い。

### 3-5. `src/lib/notion.ts` — ローカルが4関数ぶん多い

- ローカルのみ: `completeTask` / `setRemindNumber` / `findTaskByRemindNumber` / `countRemainingTasks`
- `getUpcomingTasks` のフィルタが違う:
  - origin: `期日 ≦ 明日` **かつ `期日 ≧ 今日`** → 期限切れを永久に拾わない
  - ローカル: 下限を意図的に撤去 → 期限超過も拾う
- **Notion側スキーマ要件**: ローカル版は `リマインド番号`(number) プロパティが必要。origin版のコードのままだと使われない。

### 3-6. `src/lib/line.ts` — 返信文の情報量

origin版は `buildTaskRegisteredMessage` から期日の**時刻・曜日・根拠行**が落ちている（`formatDate` も UTC解釈で曜日ズレの旧実装）。ローカル版採用。

## 4. 統合の見立て（実行はまだしない）

### 推奨: ローカル main を土台にし、origin のメール機能群を移植する

先の想定（origin土台）から反転する。理由:
- 本番＝ローカル main。土台を origin にすると、**現在動いている完了機能・期日テンプレ・CRMを一度本番から落とす**ことになる
- ローカル側の変更は「1ファイル完結」が多いのに対し、origin側は `email/` 配下がほぼ独立モジュール＝**移植しやすいのは origin 側**
- `crm.ts` はローカル版が上位互換（名寄せ・案件作成・正規化一致）

### 作業単位の見積り

| # | 作業 | 難度 | 備考 |
|---|---|---|---|
| 1 | `src/lib/email/*` `intent.ts` `contacts.ts` をローカルへコピー | 低 | 依存が閉じており、そのまま載る |
| 2 | `package.json` に3依存を追加・`npm install` | 低 | |
| 3 | `webhook/route.ts` の分岐統合 | **高** | 唯一の要設計。順序: メールセッション → 番号完了 → 引用リプライ → 曖昧確認 → #新規 → メール確定 → intent → タスク（案） |
| 4 | 画像/ファイルメッセージの受け口を追加 | 中 | ローカルは text 以外を捨てている |

| 7 | git履歴の始末（GitHubのmainをどう畳むか） | 中 | 下記 |

### git の畳み方の選択肢

- **A. ローカルmainを正としてforce push**: 履歴は綺麗になるが GitHub の PR #1〜#22 の履歴が main から外れる（PRは残る）
- **B. マージコミットで両系統を接続**: 履歴は残るが競合解決が1回で大きくなる
- **C. 統合ブランチ `integration` を切って作業 → main へPR**: ← 今回の選択（都度確認）
