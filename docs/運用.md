# 運用の手引き（帯替えのクラウド配達）

グループから頼まれた帯替えの「完成リンク」「差し戻しの知らせ」「失敗の一言」を、Mac が止まっていても出す毎分の見回り
`POST /api/obi/cloud-tick`（コードは `src/lib/obi/cloud-*.ts`）の、止め方・戻し方・見方。

**起こし方**：portal の worker（Railway。毎分動いている）が、portal の web を経由して、この入口を毎分 `POST` でたたく。**Vercel の cron は使わない**（このプロジェクトは Hobby プランで、毎分の cron を受けない。プランは変えない。`vercel.json` に、この入口の cron は無い）。
**合言葉**：ヘッダ `x-obi-tick-token` に、`HMAC-SHA256(鍵 = JOB_API_TOKEN の UTF-8, 文 = "obi-cloud-tick.v1")` の小文字16進64桁。portal と aisecretary が既に持っている `JOB_API_TOKEN` から両方が導く（Railway にも Vercel にも、新しい環境変数は足していない。`JOB_API_TOKEN` そのものは、この入口へは送らない）。`CRON_SECRET` は、この入口では使わない。
aisecretary は、1回の見回りを終えてから応答する（最長で数十秒。入口の上限 `maxDuration` は 60 秒）。portal の web は、その応答を待つ。前の回が終わる前に次の回が来ても、KV の錠（90秒）と控えの70秒の待ちで重ならない（錠が取れない回は `{ "skipped": "locked" }`）。

- 値（鍵・ID・合言葉）は、この文書に1つも書かない。変数は名前だけで呼ぶ
- 環境変数の追加・変更・デプロイ・鍵の作成は、下村さんの承認の後。値は画面・ログ・返事・コミットに出さない
- 決まりの正は、受け渡しの約束 `docs/superpowers/plans/2026-10-11-obi-cloud-contract.md`（`feat/group-obi` のブランチ）

## 0. スイッチを入れる前に確かめること

`OBI_CLOUD_DELIVERY` を入れる（初めて入れるとき・止めた後に入れ直すとき）の前に、次の3つを確かめる。

1. **portal に、`完成` のまま残っている帯替え（グループあて）が無いこと。**
   あると、入れた直後から、残っている分のリンクが毎分2件ずつ営業部のグループに出る（Mac が止まっていて配れていなかった分・人が後で配るつもりで置いてある分も、区別なく出る）。残っているなら、先に Mac に配らせるか、人が片付ける
2. **Mac が動いていて、未通知の差し戻し・失敗が無いこと。**
   スイッチを入れて最初の回は「種まき」で、その時点の差し戻し・直近7日の失敗を、全部「知らせ済み」にする（その回は知らせを1通も送らない）。Mac がまだ知らせを出していなかった分は、**どこにも出ずに終わる**。Mac が出し終えたのを見てから入れる
3. **portal の worker が、毎分この入口をたたいていること・`JOB_API_TOKEN` が、portal と aisecretary で同じ値で、32字以上であること。**
   `JOB_API_TOKEN` が無い・32字未満だと、見回りは誰も通さない（毎回 `401`。何も出ない）。値が食い違っていても `401`。値は見ない（スイッチが off のあいだに、portal からの呼び出しが `200 { "skipped": "off" }` で返っていれば、合言葉は合っている）

あわせて、段 5（変数を入れる）の決まり：

- **`OBI_CLOUD_FIX_GUIDE` は、Mac の `JOB_FIX_GUIDE` と同じにする。** Mac は 2026-10-11 に既定が on になった（`JOB_FIX_GUIDE=0` のときだけ off）ので、**段 5 では `1` を入れる**。Mac を `JOB_FIX_GUIDE=0` で動かしているときだけ、入れない。食い違うと、同じ完成の知らせでも、クラウドが出した回と Mac が出した回で末尾の案内のあり・なしが変わる
- 一覧の応答の `peers.mac.noticeClaim` が `true`（Mac が「予約を取ってから送る版」）になっていること（約束の「本番に出す順番」の段 6）

### もう一度 on にするとき（種まきは1回きり）

種まきは、初めて on にした回の1回だけ（portal が覚えている）。**Mac を前の版（予約を取らずに送る版）で動かした後に、もう一度 on にすると、前の版の Mac がもう出した差し戻し・失敗の知らせを、クラウドがもう一度出す**（portal に「知らせ済み」の印が無いため）。
再 on の前に、**差し戻しの依頼と、直近7日の失敗の依頼が残っていないこと**を確かめる（残っているなら、片付くか7日過ぎるのを待つ。または二重に出ることを承知して入れる）。

### 「資料を止めて」はクラウドには効かない

Mac の配達の停止（「資料を止めて」）は、Mac の中の印で、**クラウドの見回りは見ない**。止めているあいだも、クラウドは完成のリンクをグループに出す。閲覧ページの停止が効いていれば、そのリンクは開けない（閲覧ページの側の動きは、line-secretary の `docs/運用.md`）。**クラウドがリンクを出すことも止めたいときは、下の 1 でスイッチを off にする。**

## 1. 止める（ふつうはこれだけ）

1. Vercel の aisecretary の環境変数 `OBI_CLOUD_DELIVERY` を外す
2. **出し直す**（Vercel の変数は、出し直すまで効かない）
3. 確かめる：見回りの応答が `{ "skipped": "off" }` になる（off のあいだ、KV・portal・LINE を1回も呼ばない）

- 別の止め方：portal の側の中継（worker が毎分たたく仕組み）を止める（見回りそのものが呼ばれなくなる。手順は portal の運用の文書）。Vercel の「Disable Cron Jobs」は、この見回りには効かない（Vercel の cron を使っていないため）
- 止めた時点で `納品中` の依頼は、予約の期限（45分）で portal が `納品要確認` にする（人が「LINE に届いていた」か「もう一度納品する」を選ぶ）
- 止めた後の完成・差し戻し・失敗は、Mac が今までどおり出す（Mac が動いていれば）

## 2. 通常の戻し

1 だけ。

- **公開鍵（閲覧ページの `DELIVERY_CLOUD_PUBLIC_KEYS`）は消さない**。消すと、出済みのリンク（24時間の期限まで開ける）が、その場で開けなくなる
- KV の控え（`obi-cloud:*`）は触らない（期限で消える。次に on にした回が、残りを片付ける）

## 3. 緊急の失効（鍵が漏れた・出済みのリンクをすぐ開けなくしたい）

1. 上の 1 で止める
2. 閲覧ページの `DELIVERY_CLOUD_PUBLIC_KEYS` から、その kid を消して出し直す（**その kid のリンクは、全部開けなくなる**）
3. 新しい kid（`cloud-<年>-<月>` の形。前と違う値）で鍵を作り直し、aisecretary の `OBI_CLOUD_SIGNING_KEY`・`OBI_CLOUD_KID` と、閲覧ページの公開鍵を入れ替える
   （手順は K4 の計画 `2026-10-11-obi-cloud-k4-aisecretary.md` の Task 13 Step 5。秘密鍵は標準入力だけで渡し、画面・ファイルに出さない）
4. 両方を出し直してから、`OBI_CLOUD_DELIVERY` を入れ直す

開けなくなったリンクの依頼は、portal の依頼ボックスから人が納品し直す。

## 4. 戻す順番（出した順の逆）

クラウド off（上の 1）→ aisecretary を前のデプロイへ → Mac → 閲覧ページ → portal。

- **Mac を前の版に戻すときは、必ず先にクラウドを off にする**（Mac が「予約を取ってから送る版」でないままクラウドが on だと、差し戻し・失敗の知らせが二重になる。見回りは一覧の応答の `peers.mac.noticeClaim` が `true` のときだけ知らせを出すが、順番を守るのが先）
- **クラウドが on のまま、portal だけを前の版に戻さない**（前の版の portal は予約の応答に `via` を返さない。見回りは配達せずに予約を返し、60分は取り直さない＝そのあいだ完成リンクが出ない）

## 5. 見方

### 見回りの応答

| 応答 | 意味 |
|---|---|
| `401 { "error": "Unauthorized" }` | 合言葉（`x-obi-tick-token`）が無い・違う。`JOB_API_TOKEN` が無い・32字未満のときも、誰も通さない。スイッチより先に見る（外から、スイッチの状態は分からない） |
| `405 { "error": "Method Not Allowed" }` | `GET` で呼んだ（見回りは動かない。`POST` だけ） |
| `{ "skipped": "off" }` | スイッチが off（外への呼び出し0回） |
| `{ "skipped": "config", "problems": [...] }` | 共通の設定（portal・鍵・グループ・LINE・KV の6つ）が欠ける・形が違う。`problems` は変数の名前だけ。何も呼ばない |
| `{ "skipped": "locked" }` | 前の回がまだ動いている（か、止まった回の錠が残っている。90秒で消える）。KV が読めないときもこれ |
| `{ delivered, notSent, unknown, notices, seeded }` | その回に portal への報告が通った完成の件数（届いた・完成へ返した・届いたか分からない）／送れて結果を報告した知らせの数／その回に種まきをしたか |
| 上に `completionSkipped: "config"`・`problems` | 完成だけに要る3つ（署名鍵・kid・LIFF の ID）が欠ける。完成の配達だけ飛ばし、種まき・知らせ・控えの片付けは進めた |
| `500 { "error": "internal" }` | 見回りが例外で落ちた（ログに `cloud-tick error <例外の名前>`）。portal は呼び直さない。次の回（1分後）が続きを片付ける |

|---|---|---|

| `notice-msg-dropped <code>`・`notice-msg-gave-up`・`notice-msg-save-failed`・`notice-msg-list-failed`・`notice-msg-read-failed` | 選択肢つきの差し戻しの知らせの id の報告をあきらめた・控えられなかった（引用の返信では選べない。`#J4 1` の形なら選べる） | なし |
| `list-failed reject <符号>`・`list-failed failure <符号>` | 一覧が取れない（その一覧の知らせは出さない） | 続くなら portal を見る |

見回りそのもの

| 符号 | 意味 |
|---|---|
| `config-missing <名前,…>` | 共通の設定が欠けている（見回りを丸ごと飛ばした） |
| `lock-error`・`lock-release-failed` | KV の錠が読めない（何もしない）／外せない（90秒で消える） |
| `error <例外の名前>` | 見回りが例外で落ちた（`500`） |

符号のうち `<code>` は portal の応答の code（英大文字・数字・`_`）、`HTTP_<番号>` は code の無い応答、`timeout`・`network`・`http-5xx`・`invalid-body`・`no-time` は「答えが分からない」の内訳。`401`・`403` を受けた回は、その回の portal の仕事をそこで打ち切る。LINE を呼ぶ直前の印（`delivery/attempt`）が `401`・`403` のときは、控えを残す（消さない）。続けば、予約の期限まで5分を切った回に `not-sent config` で完成へ戻り、60分後から自動で配り直す。

### 「届いたか分からない」が出たとき

- **完成**（`unknown push-unknown`・`unknown interrupted`）：portal の依頼ボックスで、その依頼が `納品要確認` になっている。営業部のグループを見て、リンクが出ていれば「LINE に届いていた」、出ていなければ「もう一度納品する」を選ぶ。**見回りは送り直さない**（二重を避けるため、送り漏れを受け入れている）
- **知らせ**（`notice-unknown`・`notice-result …`）：Discord と依頼ボックスに「届いたか分かりません」が出る。グループを見て、出ていなければ人が伝える

### 取り直さない時間

- 同じ完成品（受付番号＋sha256）が `not-sent` で終わると、60分は自動で予約を取り直さない。3回続くと、最後から24時間
- 予約そのものが portal に断られた（`claim-skip <code>`。4xx）ときも、同じ数え方で待つ（断られ続ける依頼を毎分呼ばない）。`401`・`403`・答えが届かない回は数えない
- `delivered`・`unknown` で終えると数え直す。完成品を作り直す（sha256 が変わる）と別に数える
- 急ぐときは、portal の依頼ボックスから人が納品する（KV の `obi-cloud:retry:*` を手で消さない）

### 止まった回の続き

- LINE を呼ぶ前（控えが `prepared`・`attempt-requested`）で止まった分は、止まった回の約2分後の回が、portal の `delivery/attempt` を通してから再開する（リンクは1通だけ）
- LINE を呼ぶ直前〜直後（控えが `attempting`）で止まった分は、送り直さずに `unknown interrupted`（`納品要確認`）
- 送れた後（控えが `sent`）で止まった分は、次の回が報告の続きだけを行う

## タスクの追いかけ（TASK_FOLLOWUP）

- 入れる：Vercel の環境変数に `TASK_FOLLOWUP=1` を足して再デプロイ（下村さんの承認後）。
- 止める：`TASK_FOLLOWUP` を外して再デプロイ。状況の返事（待ち・延期・不要）は受け付けなくなり、朝のリマインドは今までどおり全件を出す。Notion の欄と、入っている値はそのまま残る。
- 入れる前に確かめること：Notion「LINEタスク」に `状況`・`次に確認する日`・`終わり方` の 3 つの欄があること（無いと、on のあいだ状況の返事と完了が失敗する）。
- 入れた日の朝のリマインド：前日までに振った番号のうち、今回載せなかったタスクの番号を消す。古いリマインドの番号で「3済」と返すと「見つかりませんでした」になることがある（新しいリマインドの番号で返してもらう）。

## タスクの候補（TASK_CANDIDATES）

- 入れる：Vercel の環境変数に `TASK_CANDIDATES=1` と `TASK_CANDIDATE_USER_IDS`（対象者の LINE userId をカンマ区切り。メンバー名簿の「LINE userId」から）を足して再デプロイ（下村さんの承認後。値は画面に出さない）。
- 止める：`TASK_CANDIDATES` を外して再デプロイ。メンションの無い発言は今までどおり何もしなくなる。控えていた候補は 5 日で消える。
- 対象者を変える：`TASK_CANDIDATE_USER_IDS` を書き換えて再デプロイ。
- 17 時に聞くのは Vercel Cron の `/api/candidates-ask`（`vercel.json`。UTC 8 時＝JST 17 時。Hobby プランでは 17 時台のどこかで 1 回動く）。ログの `[candidates-ask] sent` などで結果が分かる。`/api/remind-due` にも同じ聞き取りを相乗りさせてあるが、2026-10-12 時点でその入口が呼ばれている形跡は無かった（10 分おきに叩く外の仕組みが止まっているか、認証で弾かれている。期限前の通知「まもなく期限です」も出ていないはず）。「@AI秘書 候補」でいつでも一覧は出せる。
- 費用：メンションの無い発言のうち、対象者が関わり、依頼の言い回しを含むものだけ AI（タスク解析と同じモデル）に 1 回読ませる。増え方は Anthropic Console の使用量で見る。

## 記録の書き足し（TASK_RECORD）

- 入れる：Vercel の環境変数に `TASK_RECORD=1` を足して再デプロイ（下村さんの承認後）。
- 止める：`TASK_RECORD` を外して再デプロイ。以後のタスクには書き足さない。すでに入っている値は残る。
- 管理職の画面：Notion「LINEタスク」のビュー ①期限切れ（人別）②確認する日を過ぎた ③状況が分からない ④待ち ⑤案件が決まっていない。⑤で案件を選び、`案件の状態` を「確定」にするのは人。
- 名簿の「Notionユーザー」が空の人は、`担当（ユーザー）` が入らない（`担当者` の名前は今までどおり入る）。人が増えたら名簿に足す。
- ログに `[task-record] 書けなかった段: deal-link` が続くときは、秘書の連携（本体）に CRM_案件 を共有する。
